## Features: kept and rejected

The final model uses 30 features: the 12 originals, the 5 restored columns, and 13 new ones known at planning time. Each group was added in turn with the same Random Forests, and measured on test A.

**Keep rule:** keep a group if service MAE or late log loss improves by at least 0.5%, and neither gets worse by more than 1%.

| Group | Columns | Decision | Effect on test A |
|---|---|---|---|
| Outlet | `dock_type`, `parking_constraint`, mall window open/close | **kept** | MAE −3.2% |
| Service allowance | `service_allowance_min` (brand × dock type) | rejected | MAE −0.1%, log loss +0.6% |
| Planned slack | slack to window close and from open, planned dwell, last-stop flag | rejected | log loss +1.1% |
| Route context | stop position, stops in route, cumulative planned travel, planned route start | **kept** | MAE −1.3%, log loss −1.9% |
| Calendar | `is_payday`, `festival_ramp`, `is_holiday` | **kept** | MAE −12.4%, log loss −4.2% |
| Traffic | `speed_index` (district × planned arrival hour × monsoon) | **kept** | log loss −3.2% |
| Road conditions | `disruption_index` (district × dispatch date) | **kept** | log loss −17.4%, AUC 0.950 → 0.969 |

- **Leakage guard:** `features.py` asserts that no `actual_*`, `arrival_time`, `leave_outlet_time` or label-derived column can enter the feature list.
- **Calendar:** service time rises from 17 to 32 minutes late in a festival build-up, while order size only goes from 47 to 59 units. Receiving is slower on busy days.
- **Road-conditions assumption:** predictions are made on the dispatch morning, before deliveries start (the brief's wording), when road advisories are known. The organizers supplied the file covering the test dates. If predictions had to be made at the 4 PM cutoff the day before, this feature would not be available.
- **Planned dwell:** the planned dwell equals the service allowance at every stop that has a next leg. So "cumulative allowance minus planned dwell" was always 0, and was dropped.
- **Unscheduled waits:** the plan does not schedule the wait when a vehicle arrives early. A feature summing those waits at earlier stops was measured but not used (no gain).

## The new submission

`outputs/submission_task1.csv` keeps the template's 5,014 rows and order. See `reports/submission_comparison.txt`.

- **Mean predicted late rate:** 0.213, against 0.251 originally. February (non-monsoon) is 0.132 and March (monsoon) 0.253, consistent with history. 0% are exactly 0, against 14.2% originally.
- **Correlation with the original:** Pearson 0.81 for late probability and 0.93 for service time.
- **Largest late-probability changes:** Fresh deliveries on badly disrupted days (`disruption_index` 46–59), which the original rated 1–11% and now rate 93–98%. In training, 59% of deliveries on days with an index ≤ 60 were late.
- **Largest service-time changes:** large Style/Tech deliveries on ordinary days. Their predictions drop 38–71 minutes, and the original's 99th-percentile prediction fell from 77 to 71 minutes. None of these fall on festival or payday days. The likely reason is that the calendar and dock-type features now explain long handling that the original model could only tie to order size.
